# ADR 0022：GPU 執行環境

- 狀態：Accepted
- 日期：2026-11-24
- 相關需求：FR-ENV-13、FR-OPS-04、FR-OPS-12

## 背景

原本 GPU 列在範圍外（docs/01 §1.2），平臺政策也拒絕 `deploy.resources.reservations.devices`（docs/07 §3.6）。

現在用戶要部署需要 GPU 的服務，例如推論、影像處理。平臺的 Runner cafeca-dev-004 有一張 RTX 4060 Ti 16 GB，驅動 580.178.04。

gVisor 的 nvproxy（runsc `--nvproxy`）可以讓 gVisor 中的容器使用 NVIDIA GPU：

- 目前使用的 gVisor（release-20261116.0）支援這個驅動版本；
- 預設只開放 compute 與 utility 兩種能力；
- 只暴露 `/dev/nvidiactl`、`/dev/nvidia-uvm` 與 `/dev/nvidia#`。

用戶決定：

- 所有 member 都可使用 GPU；
- 多個環境分時共用同一張 GPU；
- 執行期與驗證都可使用，建置不給；
- 主機準備寫進 `runner-setup.sh`，在共用主機上執行前由用戶確認。

## 決策

### 1. 宣告

- 服務以 compose 標準寫法宣告：`deploy.resources.reservations.devices`，項目的 `capabilities` 為 `[gpu]`，可另帶 `driver: nvidia`。
- 會被忽略的欄位：`count`、`device_ids`、`options`。override 一律改寫成 `{ driver: nvidia, count: all, capabilities: [gpu] }`，分時共用節點上的所有 GPU。
- 仍然禁止：
  - 其他 device 類型（`capabilities` 不含 `gpu`）；
  - `driver` 不是 `nvidia`；
  - 主機裝置 `devices:`。

### 2. 解析器

- compose 已宣告 GPU 的服務，解析結果標記 `gpu: true`。
- 解析器產生的 compose 遇到下列訊號時，在 App 服務加上 GPU 宣告，並產生需要確認的低信心項目：
  - Dockerfile 以 `nvidia/cuda`、含 `cuda` 的 `pytorch/pytorch`、或含 `gpu` 的 `tensorflow/tensorflow` 為基底；
  - 依賴含 `onnxruntime-gpu`、`onnxruntime-node-gpu`、`@tensorflow/tfjs-node-gpu`、`cupy-cuda*`。
- 用戶若不需要 GPU，可以在確認頁編輯 compose 移除宣告。

### 3. 隔離

- Docker 另外註冊 runtime `runsc-gpu`：與 `runsc` 同一個執行檔，帶 `runtimeArgs: ["--nvproxy"]`。
- 只有宣告 GPU 的服務改用 `runsc-gpu`，其他服務維持 `runsc`，行為不變。
- 能力維持 nvproxy 預設的 compute、utility，不開放 graphics 與 video。

### 4. 分時共用

- GPU 不計數、不保留：只要節點的 GPU 就緒，就可以排入任意數量的 GPU 環境。
- 顯示記憶體不隔離，環境之間可能互相擠到 OOM，也看得到彼此的用量。確認頁與文件都要說明這件事。

### 5. 範圍

- production、staging 與驗證環境中宣告 GPU 的服務可以使用 GPU。
- 驗證的測試與 lint 沙箱（ADR 0020）：專案有任一 GPU 服務時，也以 `runsc-gpu` 加 `--gpus all` 執行。
- BuildKit 建置與 osv-scanner 不給 GPU。

### 6. 偵測與調度

- agent 以 `nvidia-smi` 偵測 GPU，`NodeSpecs` 新增三個欄位：
  - `gpus: [{ name, memory_mb }]`；
  - `gpu_driver`；
  - `gpu_ready`。
- `gpu_ready` 由自我檢查判定，以下四項都要成立：
  1. 偵測到 GPU；
  2. 驅動在 `runsc nvproxy list-supported-drivers` 中；
  3. Docker 已註冊 `runsc-gpu`；
  4. 探測容器以 `runsc-gpu --gpus all` 啟動，且容器內看得到 `/dev/nvidiactl`。
- 未就緒的原因記在 `gpu_check`。GPU 未就緒不影響一般的自我檢查（`isolation`）。
- 需要 GPU 的環境只調度到 `gpu_ready` 的平臺節點。沒有可用節點時回 `409`：「沒有可用 GPU 的 Runner 節點」。

### 7. 主機準備（`runner-setup.sh`）

只在主機有 `nvidia-smi` 時處理 GPU，否則略過：

1. 從 NVIDIA 官方 apt repository 安裝 `nvidia-container-toolkit`，以官方簽章金鑰驗證套件。它提供 Docker `--gpus` 需要的 prestart hook；
2. 驅動不在 gVisor 支援清單時，印出警告並略過後續步驟；
3. 在 `daemon.json` 合併 `runtimes.runsc-gpu`，其他設定原樣保留；
4. 執行 `systemctl reload docker`，不重啟既有容器。

`uninstall` 只移除 `runtimes.runsc-gpu`，不移除 toolkit。

## 考慮過的方案

| 方案 | 優點 | 缺點 |
| --- | --- | --- |
| 直接在 `runsc` 加 `--nvproxy` | 只需一個 runtime | 所有環境都帶 nvproxy，影響面大 |
| GPU 服務改用 runc | 相容性最好 | 失去 gVisor 隔離，用戶程式碼直接面對主機核心 |
| **另設 `runsc-gpu`，只給宣告 GPU 的服務（採用）** | 非 GPU 環境不受影響，GPU 環境仍在 gVisor 中 | 驅動版本必須在 gVisor 支援清單內 |
| 一次只配置給一個環境 | 不會互相擠顯示記憶體 | 用戶選擇分時共用 |

## 風險與影響

- **主機攻擊面**：nvproxy 會把驅動 ioctl 交給主機核心，NVIDIA 驅動的漏洞可能影響主機。gVisor 只放行支援清單內的 ioctl，但不驗證 DMA buffer。驅動要保持更新，並與 gVisor 的支援清單同步。
- **開放範圍**：所有 member 都可使用，平臺接受這個風險；M8 改成依方案開放。
- **共用工作站**：cafeca-dev-004 是共用工作站，Caloud 的 GPU 環境會和主機上的其他 GPU 工作分時共用。
- **協定**：`NodeSpecs` 新增 `gpus`、`gpu_driver`、`gpu_ready`、`gpu_check`；agent 依 compose 自行判斷是否需要 GPU，`EnvSpec` 不變。
